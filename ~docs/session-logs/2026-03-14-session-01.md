## Performance Optimization — Continued

### Overview

Continuation of systematic performance optimization work from the previous session.
This session focused on BLAKE3 allocation elimination and CRC-32C hardware acceleration,

### Work Completed

#### 1. BLAKE3 Allocation Elimination (commit 7fa11a6, issue #68)

**Problem:** BLAKE3 was 15.7x slower than the native Rust Blake3 library, with 2.5MB
of allocations for 1MB input. Root causes:

- `Compress()` returned a heap-allocated `uint[]` via collection expression (called 16K+
  times per 1MB)
- `First8()` created another `uint[]` per call via collection expression
- CV stack used jagged `uint[54][]` (54 separate array allocations)
- Message permutation used `stackalloc + CopyTo` per round
- Parent compression did unnecessary `uint → byte → uint` round trip via `CvToBytes`

**Changes:**

- Flattened CV stack from jagged `uint[54][]` to flat `uint[54 * 8]` array
- Changed `Compress()` from returning `uint[]` to writing to `Span<uint>` parameter
- Removed `First8()` — callers now use `output[..8].CopyTo(cv)` directly
- Removed `CvToBytes()` — parent compression packs CVs as 16 uint message words directly
- Split into `Compress()` (byte→word wrapper) + `CompressWords()` (core)
- In-place message permutation using cycle decomposition (two 8-cycles)
- Skip block copy for full 64-byte blocks in CompressChunk/CompressChunkRoot
- Use `Unsafe.ReadUnaligned` for message word loading
- Use `MemoryMarshal.GetReference` + `Unsafe.Add` for bounds-check-free state access

**Results:**

| Size | Before | After | Improvement |
|------|--------|-------|-------------|
| 1KB | — | 2.40x | — |
| 64KB | — | 8.28x | — |
| 1MB | 15.70x | **8.43x** | **1.86x faster** |
| Alloc (1MB) | ~2.5MB | **2,912 B** | **~860x reduction** |

Allocations are now **constant** regardless of input size. The remaining 8.43x gap
is the fundamental C# JIT vs native Rust/LLVM+SIMD difference.

#### 2. CRC-32C SSE4.2 Hardware Acceleration (commit db0524f, issue #69)

**Problem:** CRC-32C used byte-by-byte polynomial calculation with 8 inner-loop
iterations per byte — extremely slow compared to hardware CRC32C instruction.

**Changes:**

- SSE4.2 accelerated path: `Sse42.X64.Crc32(crc, ulong)` processes 8 bytes/instruction
- Fallback: `Sse42.Crc32(crc, uint)` for 4-byte remainder, byte-by-byte for tail
- Software fallback: 256-entry lookup table for non-SSE4.2 CPUs

#### 3. xxHash/CRC Wrapper Analysis (issue #69)

Analyzed the 1.06-1.13x overhead for xxHash32/64/3/128 and CRC-32/64. Determined this
is inherent to the streaming wrapper pattern — `HashFacade.ComputeHash()` creates
instances and returns `byte[]` vs baseline's one-shot primitives. Not an implementation
issue.

### Key Technical Insights

1. **BLAKE3 allocation was the dominant bottleneck** — collection expression returns
   in `Compress()` created ~16K heap arrays per 1MB, causing massive GC pressure.
   Eliminating allocations alone cut the ratio almost in half.

2. **Parent compression byte round trip was wasteful** — Converting uint CVs to bytes
   then parsing bytes back to uints is unnecessary when you can pass words directly.

3. **Cycle decomposition for message permutation** — The BLAKE3 permutation
   `[2,6,3,10,7,0,4,13,1,11,12,5,9,14,15,8]` decomposes into exactly two 8-cycles,
   allowing in-place permutation with just 2 temp variables instead of 16.

4. **CRC-32C hardware instruction** — SSE4.2 CRC32C processes 8 bytes per cycle vs
   64 operations (8 bytes × 8 iterations) in the old byte-by-byte approach.

5. **xxHash/CRC wrapper overhead is inherent** — The 6-13% overhead comes from the
   streaming interface lifecycle (create, update, finalize, convert to byte[]).
   Not addressable without API redesign.
