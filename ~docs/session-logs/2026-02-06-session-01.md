### Allocation Analysis

Created comprehensive analysis document: [~docs/2026-02-06-allocation-analysis.md](~docs/2026-02-06-allocation-analysis.md)

#### Key Findings

**Problem:** 91% of memory allocations come from BouncyCastle algorithms

| Source | % of Allocations | MB per 50MB file |
|--------|-----------------|------------------|
| BouncyCastle (29 alg) | 91% | ~1,087 MB |
| File buffer | 4% | 50 MB |
| Parallel overhead | 4% | 50 MB |
| Native hashes (41) | <1% | ~2 MB |

**Why BouncyCastle Is Slow:**
- Creates new byte[] arrays on every `BlockUpdate()` call
- No Span<T> optimization in internal operations
- Defensive copying of data
- Estimated ~700KB per algorithm per 1MB chunk

**Algorithm Breakdown:**
- Native implementations: 30 algorithms (~2KB state total) ✅
- .NET built-in crypto: 5 algorithms (~2KB state) ✅
- Custom StreamHash: 6 algorithms (~11KB state) ✅
- BouncyCastle: 29 algorithms (~1GB allocations) ❌

### Research: Replacement Libraries

| Library | Algorithms | Allocations | Speed | License |
|---------|-----------|-------------|-------|---------|
| **SauceControl.Blake2Fast** | BLAKE2b/s | 32B (fixed!) | 2-5x faster | MIT |
| **Blake3.NET** | BLAKE3 | ~100B | 10-20x faster | MIT |
| **System.Security.Cryptography** | SHA-1/2, MD5 | ~256B | Native speed | MIT |

**Key Insight:** SauceControl.Blake2Fast allocates only **32 bytes total** regardless of input size, vs BouncyCastle's ~7MB for 3MB input.

### Performance Optimization Plan

**Phase 1 (February 2026):** Replace BLAKE2/BLAKE3
- Expected impact: -30% allocations (1,255MB → ~875MB)
- Libraries: SauceControl.Blake2Fast, Blake3.NET

**Phase 2 (March 2026):** Native SHA-3/Keccak
- Expected impact: -20% allocations (~875MB → ~700MB)
- Implementation: SIMD-optimized Keccak permutation

**Phase 3 (April 2026):** Native RIPEMD + cleanup
- Expected impact: -20% allocations (~700MB → ~565MB)
- Final target: <12x file size (vs current 25x)
