## Summary

Ran comprehensive benchmarks and discovered that multiple algorithms were allocating 1MB+ for 1MB inputs. Fixed AcryptohashnetAdapter with ArrayPool buffering, achieving 99.9% allocation reduction.

### 2. Root Cause Analysis

**AcryptohashnetAdapter issues:**
1. `Update()` method: Called `data.ToArray()` creating full copy of input
2. `ComputeX()` methods: Also called `data.ToArray()` for one-shot compute

### 3. Fix Implementation

**AcryptohashnetAdapter.cs refactor:**

```csharp
// Added ArrayPool buffering
private const int BufferSize = 65536; // 64KB
private byte[]? _rentedBuffer;

public void Update(ReadOnlySpan<byte> data) {
    _rentedBuffer ??= ArrayPool<byte>.Shared.Rent(BufferSize);
    
    int offset = 0;
    while (offset < data.Length) {
        int chunkSize = Math.Min(BufferSize, data.Length - offset);
        data.Slice(offset, chunkSize).CopyTo(_rentedBuffer);
        _hasher.Update(_rentedBuffer, 0, chunkSize);
        offset += chunkSize;
    }
}
```

**Also added `ComputeViaStreaming()` helper** - All `ComputeX()` factory methods now use streaming to avoid `ToArray()` allocations.

### 4. Results After Fix

| Algorithm | Before | After | Reduction |
|-----------|--------|-------|-----------|
| Keccak256 | 1,049,472 B | 848 B | 99.92% |
| Ripemd160 | 1,049,128 B | 624 B | 99.94% |
| Tiger192 | 1,049,128 B | 624 B | 99.94% |
| MD4 | 1,049,104 B | 592 B | 99.94% |

### 5. SHA3 Library Limitation

**nebulae.dotSHA3** allocates internally during `Update()` calls. Attempted same fix pattern but allocations are within the library itself. Added documentation:

```csharp
/// <remarks>
/// <para>
/// <b>Allocation Note:</b> The nebulae.dotSHA3 library internally allocates
/// memory proportional to input size during Update() calls. This is a 
/// library limitation that cannot be worked around.
/// </para>
/// </remarks>
```
